# 图片数据清洗正式执行与结果报告边界

> - 适用范围：旅游 UGC 图片进入论文视觉编码、统计分析或发布数据集之前的技术噪声清洗
> - 配套数据清洗方案版本：`2.4`
> - 图片技术噪声标签手册：`image-noise-v1.0`
> - 当前工程基线：派生 schema `v25`；Issue #10 的图片子系统基线为 schema `v22`，并已由 v23–v25 迁移继续保护
> - 更新日期：`2026-08-01`
> - 证据状态：Issue #10 非人工工程验收已完成；正式图片、正式人工证据和真实清洗结果由 Issue #12 跟踪

## 1. 先给出结论

当前项目已经具备完整的图片清洗工程框架，但还没有完成正式图片清洗。

两者的区别是：

- **工程框架已经完成**：图片角色分流、受控 manifest、文件指纹、重复候选、人工任务导出、双标、仲裁、决定快照、精确 SHA 传播、保留集审计和可信证据门均已有代码、派生数据库和测试。
- **正式图片尚未落盘**：上游目前主要保存图片链接，尚未形成由研究者控制、可以冻结和复验的本地图片文件集合及正式 manifest。
- **正式人工工作尚未发生**：两名研究者还没有对真实图片完成 30 张 pilot、候选代表首标、动态第二槽和 50 张边界双标，第三人也没有执行真实仲裁。
- **真实质量审计尚未发生**：尚未从真实保留图片人口中抽取主样本和平台补充样本，因此没有真实残余噪声率、Wilson 上限或正式验收状态。

所以，当前可以说“图片清洗框架已经实现、通过合成验收并完成工程 Issue 验收”，不能说“正式图片已经清洗完成”或“图片清洗效果已经达到某个数值”。

## 2. 这份文档解决什么问题

本文件单独说明五件事：

1. 为什么正式图片必须先受控落盘；
2. 研究者需要向图片清洗流程提供什么；
3. 正式人工复核具体怎样进行；
4. 什么条件下才可以宣布图片清洗通过；
5. 在真实数据完成前，哪些结果可以报告，哪些结果禁止报告。

本文件不重新定义清洗算法、标签或阈值。科研口径以 [`../methods/数据清洗科研方案.html`](../methods/数据清洗科研方案.html) 为准，工程接口以 [`数据清洗工程方案.md`](数据清洗工程方案.md) 为准。

## 3. 四种状态不能混用

| 状态 | 含义 | 当前是否达到 |
| --- | --- | --- |
| 工程实现完成 | 代码、schema、CLI、模板、失败语义和测试已经实现 | 是 |
| 合成验收通过 | 用程序生成的非研究图片验证流程、边界和安全约束 | 是 |
| 正式执行完成 | 真实图片已经受控落盘，研究者完成规定人工任务，决定和审计已经封存 | 否 |
| 真实效果得到验证 | 可以依据真实运行报告候选量、人工耗时、一致率、噪声率和审计结果 | 否 |

合成验收只证明程序按契约运行。它不能证明：

- 上游全部真实图片都可以下载或解码；
- 真实图片中的技术噪声比例是多少；
- 候选规则对真实技术噪声的召回是否充分；
- pHash 候选对在真实数据中有多少实际帮助；
- 研究者需要多少小时完成复核；
- 最终保留图片已经达到 2% 质量门。

## 4. 为什么正式图片必须受控落盘

图片链接不是可以复验的正式图片证据。链接可能失效、重定向、返回占位内容，或在不同时间返回不同字节。SHA-256、pHash、尺寸、透明度和解码状态都必须针对实际文件字节计算。

当前清洗程序不负责联网下载。正式文件和 CSV manifest 必须由独立的上游下载/整理步骤交付；图片清洗入口只校验、导入和读取这一受控交付物。

正式落盘至少实现以下目的：

1. **冻结研究对象**：同一个图片对象在标注、决定、审计和复现时必须对应相同字节。
2. **生成文件指纹**：精确 SHA 簇和 pHash 候选必须建立在真实文件上，不能只比较 URL。
3. **识别技术失败**：缺失、下载错误、解码失败和文件变化属于自动技术状态，不应交给研究者猜测。
4. **保证可复现**：manifest、文件哈希、配置摘要和代码版本共同定义一次正式运行。
5. **保护源数据**：清洗程序只读源图片和正式采集库，所有状态、标签与决定写入独立派生 SQLite。

正式落盘不等于把图片提交到 Git。原始 UGC、作者标识和派生数据库仍不得进入仓库版本历史。

## 5. 正式开始前，研究者需要提供什么

### 5.1 必须提供

| 输入 | 研究者负责的内容 | 系统负责的内容 |
| --- | --- | --- |
| 受控本地图片目录 | 确认图片可合法用于本研究，并指定受控、只读的本地目录 | 读取文件，不修改原图 |
| 正式图片 CSV manifest | 确认本轮图片集合和采集快照，由上游下载/整理步骤生成清单 | 校验并导入稳定身份、相对路径、声明 SHA、大小和状态，不联网补抓 |
| 两名独立标注者 | 分别完成 pilot、正式槽位和边界集任务 | 隐藏另一人的标签，校验匿名身份和任务完整性 |
| 一名第三仲裁者 | 只处理两槽分歧或任一 `uncertain` 的对象 | 阻止无必要仲裁，并绑定两条原始证据 |
| 标签手册确认 | 在 pilot 后确认或修订 `image-noise-v1.0` 的边界示例 | 保存手册版本，禁止跨版本拼接证据 |
| 正式标注文件 | 按系统导出的任务逐行填写标签和安全理由代码 | 校验字段、追加导入、重算一致率和决定门 |

### 5.2 不需要研究者提供

研究者不需要：

- 手工计算 SHA-256 或 pHash；
- 自行挑选 pilot、边界集或审计样本；
- 重新判断图片是头像、页面图还是内容图；
- 为缺失、损坏或解码失败的文件贴人工语义标签；
- 全量查看所有普通非候选内容图；
- 填写一致率、Cohen's kappa、Wilson 上限或“通过/失败”；
- 判断图片是否美观、是否为实景、是否商业推广，或是否符合论文目的地形象编码。

这些项目要么由冻结来源事实决定，要么由程序从原始证据重算，要么根本不属于图片清洗任务。

## 6. 正式人工只标一个轴

唯一必填人工标签是：

```text
technical_noise_label =
  valid_content
  | site_background
  | site_ui
  | placeholder_or_error
  | tracking_or_qr_only
  | uncertain
```

标签含义如下：

| 标签 | 含义 | 默认动作 |
| --- | --- | --- |
| `valid_content` | 图片仍具有帖子内容或旅行信息价值 | 保留 |
| `site_background` | 平台或站点背景、通用装饰素材 | 拟排除，须双标或仲裁 |
| `site_ui` | 平台 UI、按钮、页面框架或无内容价值的界面截图 | 拟排除，须双标或仲裁 |
| `placeholder_or_error` | 占位图、加载失败图或错误提示图 | 拟排除，须双标或仲裁 |
| `tracking_or_qr_only` | 只有追踪、跳转或引流作用，没有独立内容价值 | 拟排除，须双标或仲裁 |
| `uncertain` | 证据不足，暂时无法稳定判断 | 保留或继续复核，禁止直接排除 |

路线图、推荐计划图、攻略卡、地图、菜单、票据、海报和信息图都可能是有效内容。文字密集、低分辨率、水印、商业推广或含二维码，均不能单独成为排除理由。只有图片实质上仅剩追踪或引流功能时，才考虑 `tracking_or_qr_only`。

## 7. 正式执行流程

### 7.1 冻结图片文件与 manifest

1. 将本轮正式图片放入研究者控制的本地目录；
2. 由独立上游下载/整理步骤生成只包含必要身份、相对路径和文件事实的 manifest；
3. 校验文件存在、大小、SHA 和可解码状态；
4. 记录配置摘要、代码提交、随机种子和采集快照身份；
5. 封存运行后不得替换原文件或静默修改 manifest。

图片文件仍保持只读。文件失败进入自动技术状态，不进入人工标签量。

### 7.2 消费冻结来源角色与候选

系统直接消费 Issue #9 已冻结的来源角色：

- `author_avatar`：自动离开内容图片视图；
- `page`：保存为 `evidence_only`；
- `content`：才可以进入图片技术噪声候选和人工复核。

SHA 精确簇代表是候选复核的主要人工单位。pHash `d≤10` 和其他技术信号只负责组织候选，不提供真值，也不自动排除图片。

### 7.3 完成 30 张 pilot

从真实候选中稳定抽取 `min(30, N_candidate)` 张。正式大样本时为 30 张，两名研究者分别独立判断，因此产生 60 个判断。

pilot 的作用是：

- 发现标签定义是否存在理解差异；
- 收集真实边界示例；
- 记录单张标注耗时；
- 冻结或修订标签手册。

pilot 不产生逐图正式排除决定，也不进入总体噪声率估计。完整双标且原始一致率达到 0.80，才可以打开正式决定门。

### 7.4 完成候选代表首标和动态第二槽

1. 第一名研究者对全部候选代表完成 slot 1；
2. 明确的 `valid_content` 且不属于边界集时，可以停在单标保留；
3. slot 1 为四类拟排除标签或 `uncertain` 时，系统冻结 slot 2；
4. 第二名研究者独立完成 slot 2，不能看到第一人的答案；
5. 两人一致的拟排除标签可以形成排除证据；
6. 两槽分歧或任一 `uncertain` 必须交第三人仲裁；
7. 两槽已经一致且均非 `uncertain` 时，禁止第三人任意改判。

### 7.5 完成 50 张边界盲双标

系统另行冻结 `min(50, N_total)` 张候选与保留边界样本。正式大样本时为 50 张，两名研究者各判断一次，共 100 个判断。

边界集只用于检验手册可重复性：

- 报告原始一致率；
- kappa 可估时报告 Cohen's kappa；
- 只有单一类别等情况导致不可估时，保存 `NULL` 和明确原因；
- 原始一致率低于 0.80 时，修订手册并建立新的 review run；
- 不跨 run、手册版本或标注槽位拼接证据。

边界集经过困难案例富集，不能用来估计总体技术噪声率，也不能直接产生逐图正式决定。

### 7.6 形成决定并进行精确 SHA 传播

正式决定只能消费同一 formal candidate review 中的可信证据：

- 拟排除必须有双人同意或合法仲裁；
- `uncertain` 保持 `review/keep`；
- pilot 和 boundary 的逐图标签不能越权生成正式决定；
- 单人 `valid_content` 只能支持当前代表保留，不能传播；
- 只有双人同意或仲裁形成的技术噪声标签，才可传播到字节完全相同的 SHA 簇成员；
- pHash 组在任何情况下都不能传播标签或排除决定。

### 7.7 运行真实保留集两层审计

审计单位是决定应用后的当前保留 `content` 图片关系，不是候选代表总体。

设第 `r` 轮的当前真实人口为 `N_r`，其中没有在旧轮出现、或虽曾出现但已经随新决定离开当前人口后重新形成的可抽人口为 `E_r`。第一轮没有历史排除，因此 `E_1=N_1`。

第一层为 `primary`：

- 从 `E_r` 中等概率、稳定、无放回抽取 `min(200, E_r)`；
- 第一轮人口少于 200 时完整普查；
- 后续轮只有在 primary 实际完整覆盖本轮全部当前人口、补充层为空且每项纳入概率和权重均为 1 时，才属于 census；
- 已退出当前人口的旧轮身份不妨碍新的完整普查；仍属于当前人口的旧轮成员必须保持不复抽，因此这时不能把较小的可抽子集称为 census；
- 非普查时只用 primary 的事件数计算总体点估计和单侧 95% Wilson 上限。

第二层为 `platform_supplement`：

- 若平台 `p` 在 primary 中少于 `min(30, N_p)`，从该平台剩余可抽人口补足缺口；剩余人口不足时全取，不允许复抽旧成员或虚报已经观察满 30 张；
- 补充层不进入总体点估计或 pooled Wilson；
- 任一补充样本出现技术噪声或 `uncertain`，本轮即不通过。

主样本门如下：

- census：真实残余技术噪声率不超过 2%；
- 非 census：点估计和单侧 95% Wilson 上限均不超过 2%；
- `0/200` 的单侧 95% Wilson 上限约为 1.3347%，可以通过；
- `1/200` 的单侧 95% Wilson 上限约为 2.2098%，不能通过。

失败后必须先修正规则或人工决定，形成 manifest 已变化的新决定版本，才可进入下一轮。下一轮使用协议种子 `base_seed + round_number - 1`，并排除仍位于当前人口中的旧轮成员。最多三轮，仍未通过时保持 `review`。

### 7.8 封存正式运行证据

正式完成后至少封存：

- 图片和人口 manifest 摘要；
- 配置、手册、随机种子和代码版本；
- pilot、边界集、正式槽位和仲裁的原始证据；
- 一致率、可估或不可估的 kappa 状态；
- 决定快照和精确 SHA 传播成员 manifest；
- 每轮 primary、平台补充、纳入概率、权重和样本 manifest；
- 残余事件数、点估计、区间上限和最终状态；
- 失败、修订决定和重试之间的版本谱系。

所有正式证据写入独立派生 SQLite，不回写正式采集库。

## 8. 人工工作量怎样计算

图片清洗没有一个可以在真实图片落盘前预先承诺的固定标注总量。

设：

- `P = min(30, N_candidate)`：pilot 图片数；
- `C`：候选 SHA 代表数；
- `D`：首标后拟排除或 `uncertain`、需要第二槽的代表数；
- `B = min(50, N_total)`：边界集图片数；
- `J`：实际需要第三人仲裁的对象数；
- `N_r`：第 `r` 轮当前保留人口数；
- `E_r`：排除仍在当前人口中的旧轮成员后，本轮可抽人口数；
- `R_{p,r}`：primary 冻结后，平台 `p` 的剩余可抽人口数；
- `A_r`：第 `r` 轮保留集审计任务数。

则正式人工判断量按下式理解：

```text
基础复核判断量 = 2P + C + D + 2B + J

A_r = min(200, E_r)
      + Σ_p min(R_{p,r}, max(0, min(30, N_{p,r}) - m_{p,r}))

总判断量 = 基础复核判断量 + Σ_r A_r
```

其中 `m_{p,r}` 是第 `r` 轮 primary 中平台 `p` 的数量。第一轮有 `E_1=N_1`；后续轮若旧样本仍在当前人口中，`E_r` 可能小于 `N_r`。若一致率不足而追加边界补充轮，还需增加该补充轮的实际双标判断数。

这只是工作量结构。正式预算必须以系统实际导出的任务 manifest 为准，因为候选规模、首标分布、平台构成、样本重叠、仲裁率和审计轮数都只有在真实数据运行后才知道。同一图片即使跨 pilot、boundary 和 formal run 出现，也不能由研究者自行合并证据；系统导出的任务身份是计数依据。

## 9. 研究者实际填写什么文件

仓库中的空白 CSV 只定义列契约：

- [`../../data/annotations/templates/image-technical-noise-annotations.csv`](../../data/annotations/templates/image-technical-noise-annotations.csv)
- [`../../data/annotations/templates/image-technical-noise-adjudications.csv`](../../data/annotations/templates/image-technical-noise-adjudications.csv)
- [`../../data/annotations/templates/image-keep-audit-annotations.csv`](../../data/annotations/templates/image-keep-audit-annotations.csv)

正式标注不能直接复制空白模板后自行填对象编号。必须从具体封存运行中导出任务，以保留 review run、slot、fingerprint、guide version 和样本层身份。

研究者只填写系统指定的标签、理由代码、匿名标注者身份和时间等字段，不修改对象身份列、版本列或抽样列。身份使用项目规定的匿名哈希；理由代码不得写入真实姓名、绝对路径、自由文本隐私信息或电子表格公式。

## 10. 什么条件下才算正式图片清洗完成

下列条件必须全部满足：

- [ ] 正式图片已受控落盘，manifest 已封存且文件校验完成；
- [ ] 头像、page、技术失败和 `content` 的自动分流已完成；
- [ ] 30 张真实 pilot 已由两人独立完成，原始一致率达到 0.80；
- [ ] 候选代表 slot 1 已完成；
- [ ] 所有拟排除和 `uncertain` 代表均完成 slot 2；
- [ ] 所有分歧或 `uncertain` 已由第三人仲裁；
- [ ] 50 张真实边界盲双标已完成，原始一致率达到 0.80；
- [ ] 正式决定快照和允许的精确 SHA 传播已封存；
- [ ] 当前保留人口、primary 和平台补充 manifest 已封存；
- [ ] 主样本达到 2% 质量门，平台补充层没有技术噪声或 `uncertain`；
- [ ] 配置、手册、代码、输入和输出版本可以完整追溯；
- [ ] 质量报告没有把定向样本、边界集或合成夹具当成总体概率证据。

任一硬门未满足时，正式运行状态只能是 `blocked`、`review` 或 `failed`，不能写成“清洗通过”。

## 11. 当前可以报告什么

在正式图片落盘和人工执行前，可以报告：

- 图片清洗工程框架已经实现；
- 当前仓库派生 schema 为 v25；图片复核、决定与审计子系统在 schema v22 完成，v23–v25 继续迁移并增加文本双轴、最终发布和图片传播/验收约束；
- 系统只使用 `technical_noise_label` 作为人工图片清洗轴；
- 头像和页面图由来源角色自动分流；
- pHash 只生成和组织候选，只有精确 SHA 可以在严格证据门下传播技术噪声标签；
- 两层保留集审计、证据封存和直接 SQL 防绕过约束已经实现；
- 合成与受控夹具测试证明流程可以在断网、源文件只读条件下运行；
- Issue #10 完成时的历史基线为 `209 passed`，独立复审为 P0=0、P1=0、P2=0；合并 Issue #11 与最新 main 后的 2026-08-01 全库基线为 `332 passed, 8 warnings`。

这些都是工程和协议事实，不是正式数据结果。

## 12. 当前禁止报告什么

在真实运行完成前，不得报告或暗示：

- “真实图片已经清洗完成”；
- 真实候选图片数量或候选占比；
- 真实头像、页面素材、占位图、UI 图或追踪图比例；
- 真实图片可下载率、解码率或文件失败率；
- 真实人工标注耗时或总人时；
- 真实 pilot、边界集或正式标签的一致率与 kappa；
- 真实仲裁数量或仲裁率；
- 真实残余技术噪声率或 Wilson 上限；
- 真实保留图片数量、排除数量或清洗提升幅度；
- pHash 候选在真实数据中的 precision、recall 或自动传播效果；
- 合成测试中的 `passed` 可以代表正式研究验收。

不存在的数据不能用“预计”“大概”包装成结果。可以把数量写成待运行字段或工作量公式，但不能填入未经正式证据支持的数值。

## 13. 正确与错误的报告示例

### 13.1 当前阶段的正确写法

> 项目已实现图片来源角色分流、文件指纹、技术噪声人工复核、精确 SHA 标签传播和两层保留集审计框架，并以合成夹具验证断网执行、证据封存与源文件只读边界。由于正式图片尚未按受控 manifest 落盘，真实人工复核和保留集审计尚未执行，本文不报告真实图片噪声率、人工耗时或清洗效果。

### 13.2 当前阶段的错误写法

> 图片清洗已经完成，系统能够准确删除头像、背景图和无效图片，最终噪声率低于 2%。

错误原因：头像分流虽然是确定性功能，但“正式清洗完成”“准确删除”和“低于 2%”都需要真实图片、真实人工证据和真实保留集审计支持。

### 13.3 正式运行后的结果写法框架

正式运行完成后，结果至少应包含：

```text
正式图片快照：<snapshot / manifest identity>
配置与代码版本：<config digest / commit>
成功落盘与技术失败：<真实计数>
候选 SHA 代表：<真实计数>
pilot：<样本数、原始一致率、kappa 状态、耗时>
边界集：<样本数、原始一致率、kappa 状态>
正式复核：<slot 1、slot 2、仲裁的真实计数>
决定与 SHA 传播：<保留、排除、复核、传播的真实计数>
审计主样本：<primary 数、事件数、点估计、区间方法、上限>
平台补充：<各平台样本数、事件数>
最终状态：<passed / review / failed>
```

所有数值必须能够回到封存的原始标注、决定版本、人口快照和审计 manifest。
