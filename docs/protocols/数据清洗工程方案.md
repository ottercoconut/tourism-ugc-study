# 数据清洗工程方案

## 1. 文档状态

- 方案版本：`3.0`
- 派生 schema：`30`
- 文本标签手册：`text-cleaning-v1.0`
- 配套科研方案：`docs/methods/数据清洗科研方案.html`
- 配套人工方法：`docs/protocols/文本数据清洗人工标注方法.md`
- 固定运行环境：CPython 3.13.5，命令统一通过 `.venv/bin/python`

v3.0 将数据清洗边界收缩为“帖子结构可用性、旅游相关性与文本重复关系”。
清洗阶段不读取、下载、解码、标注、筛选或发布任何媒体文件，也不要求上游提供
媒体关系表。媒体内容及其角色、质量和研究编码属于后续视觉研究阶段；相关的上游
关系语义问题继续保留在 GitHub Issue #18 中，但不构成本流程的输入门或质量门。

科研方案与工程方案共享版本。标签、抽样、阈值、算法或决策状态变化时，必须在
同一 commit/PR 中同步更新两份文档。

## 2. 目标与非目标

### 2.1 目标

1. 只读冻结正式采集 SQLite，并验证青岛输入范围契约。
2. 对帖子文本进行确定性规范化、结构检查和重复候选生成。
3. 以少量概率样本和边界样本建立可追溯人工双轴证据。
4. 用泄漏安全的线性文本基线扩展复核顺序，不让模型覆盖人工证据。
5. 形成版本化帖子最终决定、保留集审计、确认重复关系和分析去重结果。
6. 发布两个显式绑定 `run_id/release_id` 的帖子集合，并保留配置、代码、快照、
   人工证据和成员 manifest 的完整谱系。

### 2.2 非目标

- 不生成逐条城市标签；城市范围是运行级输入契约。
- 不以互动量、商业属性或平台身份作为清洗标签。
- 不对媒体资产做任何预处理或质量判断。
- 不把近重复候选阈值直接当作排除规则。
- 不把模拟标注、合成夹具、smoke 模型或工程测试写成正式科研证据。
- 不回写正式采集数据库。

## 3. 输入契约与快照

清洗所需源表只有：

| 表 | 必需字段 |
| --- | --- |
| `schema_migrations` | `version`、`name`、`applied_at` |
| `source_platforms` | `platform_key` |
| `web_posts` | `id`、`platform_key`、`source_type`、`source_url`、`title`、`author_platform_id`、`published_at`、`captured_at`、`content_text`、`status` |

当前源库若没有 `city_name`，必须存在上游迁移
`(13, "remove_city_name")`；旧库若仍有 `city_name`，所有非空值只能属于配置中的
`青岛/青岛市`。范围不满足时，整个运行记为 `input_rejected`，不得转写成逐条标签。

`snapshot_source` 使用 SQLite 只读 URI 和 backup API 冻结一致性快照，记录源文件
前后 SHA-256、快照 SHA-256、帖子数、帖子主键 manifest、配置摘要、代码版本和
环境版本。对象 manifest 只覆盖 `web_posts.id`。源文件在复制期间变化、完整性检查
失败、外键失败或必需表/列缺失时，运行拒绝继续。

## 4. 配置与版本锁

主配置为 `configs/cleaning-v3.0.yaml`。核心字段包括：

```yaml
protocol_version: "3.0"
text_label_guide_version: "text-cleaning-v1.0"
random_seed: 20260728

algorithm_versions:
  derived_schema: 30
  inventory: "source-inventory-v2-text-only"
  scheduler: "incremental-scheduler-v2-text-only"
  text_deterministic: "text-deterministic-v1"
  text_normalization: "text-normalization-v1+sha256:<digest>"
  text_runtime: "text-runtime-v1+sha256:<digest>"
  text_relevance: "text-relevance-v1"
  finalize: "cleaning-decision-v2-text-only"
```

确定性规则保存在 `configs/cleaning-text-normalization-v1.yaml`。主配置同时锁定规则
文件字节摘要和文本运行时摘要；任一不一致都拒绝复用旧结果。共享配置不得包含
令牌、本机绝对路径、源库路径、派生库路径或人工身份清单。

## 5. 增量任务图

清洗对象只有 `post`，每个帖子版本只包含三个必需阶段：

```text
text_deterministic → text_relevance → finalize
```

| 输入变化 | 重跑范围 |
| --- | --- |
| 标题、正文、状态或来源类型变化 | 三个阶段全部重跑 |
| 作者平台身份变化 | `text_relevance`、`finalize` |
| 互动量、发布时间、来源 URL 等分析字段变化 | 不创建清洗任务，只登记 `analysis_only` 新版本 |
| 算法版本变化 | 从变化阶段起向下游传播 |

任务 ID 由运行、阶段、对象、源版本和有效算法版本稳定计算。批次按
`captured_at,id` 冻结帖子及其全部待处理任务；所有任务均为必需任务。任务状态为
`pending → running → succeeded/failed/blocked/skipped`，失败或阻塞必须显式恢复，
不能由读取动作自动重试。计算完成只使运行进入 `quality_gate_pending`，不能自动
变成 `accepted`。

## 6. 确定性文本处理

规范化依次执行 Unicode NFKC、不可见格式字符处理、换行/空白统一、标题与正文
结构化组合。输出保存规范文本、结构状态、理由码、规范 SHA-256、精确文本哈希、
运行时摘要和规则摘要；原始源库不变。

结构状态：

- `usable`：标题或正文至少一项具有可辨认实际语义；
- `invalid`：双空、删除/登录/错误占位、纯技术提示或不可辨认损坏；
- `uncertain`：程序无法稳定判断，进入人工复核。

精确哈希只用于确定相同规范文本。字符 n-gram 相似度只产生近重复候选，
`final_threshold` 在人工文本对校准前保持 `null`；候选关系不得直接进入分析去重。

## 7. 人工双轴与抽样

人工标签只有两个轴：

1. `structure_label = usable | invalid | uncertain`
2. `tourism_label = related | unrelated | uncertain | not_applicable`

约束：`structure_label=invalid` 当且仅当
`tourism_label=not_applicable`。商业推广、文本长短、错别字或普通表达本身都不是
排除理由。

初始抽样由配置冻结：概率样本 500、各平台概率层最低 80、定向边界样本 200、
双标样本 200；原始一致率最低 0.80、Cohen’s κ 最低 0.70，不足时追加 100 条
双标。正式样本量按实际总体取 `min(目标,N)`，不要求为了测试手工标注固定大数。
定向样本只服务边界学习，不进入总体比例估计。

人工文件由具体抽样运行导出，标注者使用 64 位小写十六进制匿名哈希；原始标注、
仲裁和模型复核均只追加。模拟 agent 结果只能用于可行性测试，不能进入正式双人
证据、一致率、κ、金标或论文结果。

## 8. 文本模型与决定

线性基线使用字符 n-gram TF-IDF 与线性 SVM。切分先按确认重复关系和作者身份
建立泄漏组，再做时间/平台约束切分。模型只输出候选概率、margin 和复核顺序：

- 人工最终证据优先于模型；
- `uncertain`、高风险错误和模型分歧进入复核；
- 模型不能写入或覆盖人工标签；
- 未满足配置中的 precision/recall 门槛时不得自动扩张决定。

帖子决定遵循非循环链：

```text
候选决定 → 候选 keep 人口 → 文本保留集审计 → final 决定
           → 确认重复关系 → 分析去重 → 发布
```

最终纳入的概念条件是 `usable + related`。自动扩张能否达标必须由独立测试集、平台
分层指标和保留集审计证明，不能仅凭 pilot 或训练集表现宣称。

## 9. 派生数据库

schema v30 是新的纯文本建库契约。它保留：

- 运行、帖子快照、帖子库存/版本/观察；
- 帖子阶段任务、批次和事件；
- 确定性文本、候选、精确簇、近重复候选；
- 抽样、人工标注、仲裁、一致性、泄漏组和文本模型；
- 帖子候选/最终决定、文本保留集审计；
- 文本分析去重；
- 两个帖子发布集合、报告、manifest 和验收证明。

schema 不包含任何媒体清洗表、任务或触发器。旧版派生库包含不同领域契约，不能
就地升级为 v30；必须归档旧库并从只读源快照重新构建。这样可避免旧状态被静默
解释成新研究证据。

## 10. 发布与验收

发布集合只有：

- `analysis_posts_eligible`：final 决定为 `keep` 的全部帖子版本；
- `analysis_posts_deduplicated`：上述人口每个确认重复簇的唯一稳定代表。

`cleaning_release.py build` 必须显式接收：

- final `post_decision_build_id`；
- finalized `text_dedup_build_id`；
- passed `text_keep_audit_evaluation_id`。

`formal` 发布只有在以下条件全部满足时才能接受：输入快照有效、文本审计通过、
没有 `review` 决定、全部必需任务完成、成员和 manifest 可重算、本地发布包未被
篡改、只读快照再次通过完整性检查。验收在单一事务中依次写 attestation、接受
运行、接受发布；任一步失败都回滚。

## 11. 命令

```bash
.venv/bin/python scripts/cleaning_snapshot_source.py \
  --source-db <SOURCE_DB> --derived-db <DERIVED_DB> \
  --config configs/cleaning-v3.0.yaml --run-id <RUN_ID>

.venv/bin/python scripts/cleaning_discover_increment.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.0.yaml \
  --snapshot-id <SNAPSHOT_ID>

.venv/bin/python scripts/cleaning_create_batch.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.0.yaml \
  --run-id <RUN_ID> --max-posts 1000

.venv/bin/python scripts/cleaning_process_text.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.0.yaml \
  --text-config configs/cleaning-text-normalization-v1.yaml \
  process --batch-id <BATCH_ID> --drain

.venv/bin/python scripts/cleaning_release.py --derived-db <DERIVED_DB> build \
  --run-id <RUN_ID> --release-id <RELEASE_ID> --release-mode formal \
  --post-decision-build-id <FINAL_POST_BUILD> \
  --text-dedup-build-id <DEDUP_BUILD> \
  --text-keep-audit-evaluation-id <TEXT_AUDIT> \
  --output-root <OUTPUT_ROOT>
```

所有命令只输出去敏 ID、状态、计数和哈希。参数错误或底层异常不得把正文、作者、
源路径或访问凭据写入日志。

## 12. 验证与报告边界

工程验证：

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m compileall -q src scripts tests
git diff --check
```

只有真实双人标注、真实仲裁、正式模型、正式保留集审计和 formal 发布验收完成后，
才能报告正式清洗比例、模型指标和最终样本量。合成测试和模拟研究员运行只能证明
接口可行，不能作为论文中的人工证据或研究结果。
