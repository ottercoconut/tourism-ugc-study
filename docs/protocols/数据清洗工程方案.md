# 数据清洗工程方案

- 科研协议：`3.2`
- 标签手册：`text-cleaning-v1.4`
- 主配置：`configs/cleaning-v3.2.yaml`
- 派生 schema：`33`

## 1. 工程边界

正式采集库始终只读。系统先创建 SQLite 快照，再把规范化文本、抽样、人工证据、模型、帖子决定、终验和发布记录写入派生库。清洗阶段不读取或筛选媒体文件，也不回写原始 UGC。

正式人工任务只有 `tourism_label`，其目标是判断文本是否以青岛旅游为主要内容。`structure_status` 仅存在于全量确定性处理结果和候选构建门禁中，不导出为人工字段；任何非 `usable` 记录都会使正式候选决定构建失败，等待上游隔离并重新冻结快照。

## 2. 配置

```yaml
protocol_version: "3.2"
text_label_guide_version: "text-cleaning-v1.4"
algorithm_versions:
  derived_schema: 33
  annotation_sampling: "annotation-sampling-v2-component-diverse"
annotation:
  initial_probability_size: 500
  initial_targeted_size: 200
  periodic_increment_posts: 2000
  periodic_probability_size: 100
```

已删除 `initial_recheck_size`、`minimum_recheck_interval_days`、一致率/κ 门槛和补充复检配置。旧配置不能冒充 v3.2 运行。

## 3. 活动数据契约

### 3.1 人工任务 CSV

```text
task_id,sample_run_id,source_post_id,source_version,platform_key,normalized_model_text,tourism_label
```

导入端接受 `related | unrelated | uncertain`，并明确拒绝含 `reason_codes`、`structure_label`、`review_round` 或 `commercial_label` 的旧模板。原因码不属于清洗学习输入，也不保存自由文本备注；`uncertain` 不要求出现。空字符串不是标签，只表示尚未完成人工审核，并在正式导入时被拒绝；`uncertain` 是已完成的显式判断，必须进入后续确认。

CSV 不保存逐行编码者哈希或人工填写时间。轮次级 `finalized_at_utc` 写入 manifest，数据库在导入操作及每条落库记录上自动写入 `created_at_utc`；这两层时间足以证明文件冻结和导入顺序，不补造无分析用途的逐条时间。

通过结构门后若仍出现多个来源或主题异常拼接的抓取污染，原审核记录不得静默删除或改写为空白；应保存 `uncertain` 人工证据并路由到最终确认。结构门判断文本是否可处理，人工标签判断当前可见语义能否稳定归入青岛旅游，两者不互相替代。

### 3.2 派生表

- `text_deterministic_results.structure_status`：全量自动结构门证据；
- `text_sampling_runs` / `text_sample_members`：冻结概率、定向或新增窗口样本及纳入概率；
- `text_post_annotations`：一次性人工相关性记录；
- `text_post_adjudications`：不确定项、模型边界项或其他显式最终确认；
- `text_model_runs` / `text_model_predictions`：不可变模型运行与候选动作；
- `post_decision_builds` / `post_decisions`：候选和最终帖子决定；
- `text_keep_audit_*`：自动保留候选的冻结概率终验；
- `analysis_release_*`：最终发布与验收证明。

schema 33 不再创建延时复检、补充复检或一致性评估表；原始人工记录不保存逐行编码者哈希或人工填写时间，活动人工表和帖子决定表也不保存结构标签。旧 schema 32 派生库必须显式重建，不提供兼容迁移。

## 4. 运行顺序

所有 Python 命令使用 `.venv/bin/python`。

```bash
.venv/bin/python scripts/cleaning_snapshot_source.py \
  --source-db <SOURCE_DB> --snapshot-dir <SNAPSHOT_DIR> \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  --run-id <RUN_ID> --code-version <GIT_SHA>

.venv/bin/python scripts/cleaning_discover_increment.py \
  --source-db <SNAPSHOT_DB> --derived-db <DERIVED_DB> \
  --config configs/cleaning-v3.2.yaml --run-id <RUN_ID>

.venv/bin/python scripts/cleaning_process_text.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  --run-id <RUN_ID>

.venv/bin/python scripts/annotation_export_tasks.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  create-initial --candidate-build-id <BUILD_ID>

.venv/bin/python scripts/annotation_export_tasks.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  export-post --sample-run-id <SAMPLE_RUN_ID> --output <TASKS.csv>

# 抽样规则更新且存在历史完成表时，用身份复用标签并单独导出待标记录。
.venv/bin/python scripts/annotation_export_tasks.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  export-post --sample-run-id <SAMPLE_RUN_ID> --output <OPTIMIZED.csv> \
  --reuse-labels-from <PREVIOUS_COMPLETED.csv> \
  --pending-output <PENDING.csv>

# 待标表完成后，必须合回当前完整样本并生成唯一正式完成表。
.venv/bin/python scripts/annotation_export_tasks.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  finalize-post --base <OPTIMIZED.csv> --pending <PENDING.csv> \
  --output <COMPLETED.csv>

.venv/bin/python scripts/annotation_import_annotations.py \
  --derived-db <DERIVED_DB> --config configs/cleaning-v3.2.yaml \
  --input <COMPLETED.csv> --imported-by-hash <HASH> post-reviews
```

随后按显式 ID 清单构建泄漏分组、训练相关性模型、完成模型边界项最终确认、冻结候选决定、执行保留集审计、构建最终决定和发布包。任何步骤不得使用“最新一条标签”之类的隐式选择。

`OPTIMIZED.csv` 与 `PENDING.csv` 只是同一轮人工工作的临时输入。`finalize-post` 会验证待标身份恰好覆盖 base 中全部空标签、拒绝越界/遗漏/非法值，并输出一张全标签 `COMPLETED.csv`。输出通过哈希和行数校验后，轮次目录只保留该完成表与 manifest；旧任务表、修复副本、优化表、待标表和预览图均不得继续作为平行数据源。

## 5. 关键不变量

1. 正式候选决定必须被同一快照的一帖一条确定性结果完整覆盖，且全部为 `usable`。
2. 概率样本配额从零按平台人口占比以最大余数法分配，并保存纳入概率和权重。
3. 定向样本不按平台分配且没有总体权重；它与概率样本在近重复候选分量层面互斥，并且每个候选分量最多选择一个帖子代表。
4. 近重复候选分量只约束抽样多样性；近重复确认使用独立任务和证据，不能由候选分量直接推导。
5. 同一抽样运行中的同一帖子版本只能有一条原始人工相关性记录；规则修订后的标签复用只按冻结帖子身份匹配，不读取标签值，并生成优化 manifest。
6. 概率样本保留自然出现的重复帖子和原抽样权重；构建模型参考集时，每个精确重复簇或已确认近重复分量最多选择一个代表项。
7. 作者、精确重复和确认近重复共同形成泄漏分组，同组不得跨训练、验证和测试；作者边不等于重复边，不得因此只保留同一作者的一条记录。
8. 模型只产生 `high_risk_review`、`manual_review` 或 `low_risk_keep_candidate`，永不直接产生排除。
9. 人工证据优先于模型；冲突或不确定均进入 `review`。空白标签仅表示任务未完成，不得参与训练、评价或帖子决定。
10. 低风险自动保留必须通过正式运行、切分隔离、阈值、逐平台抽审和保留集终验。
11. 候选决定与最终决定分开封存，最终决定绑定实际通过的审计 ID。
12. 样本、标签、模型、决定和发布成员均追加式或封存后不可变。
13. 一个已完成的人工轮次只有一张权威 CSV；抽样、复用和待标中间表不得与完成表并列长期保留。

## 6. 验收输出

最终验收包至少包含：

- 配置摘要、代码版本、运行环境和源快照 manifest；
- 五个平台的源数量和全量结构门计数；
- 概率/定向/新增监测样本计数与标签分布；
- 独立测试集总体和逐平台指标；
- 模型高风险、边界、低风险及人工最终确认数量；
- 保留集终验样本、事件数、点估计、单侧上限与平台切片；
- 最终 keep/review/exclude 数量及分析发布 manifest；
- 未执行的证据必须明确标为未执行，不得由测试通过状态代替。

## 7. 迁移说明

v3.2 是破坏性派生 schema 变更。正式数据尚未按旧人工契约生产，因此不迁移或伪造旧结构字段；应从只读源快照重新建立派生库。若本地存在 v31 开发库，只作历史调试材料，不可与 v32 正式运行混用。
