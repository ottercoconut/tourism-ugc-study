## 1. 这份手册解决什么问题

本手册从零说明：如何把已经完成文本规范化的青岛 UGC，交给人工标注员进行独立判断，经过一致性检查和第三人仲裁，最终形成可追溯、可复现、可用于旅游相关性模型训练的金标样本。

完成本手册流程后，应得到四类成果：

1. **原始人工标注**：每位标注员独立提交的结构、旅游相关性和商业属性判断。
2. **一致性报告**：三个判断轴各自的原始一致率和 Cohen's κ，以及计划完成状态。
3. **仲裁金标**：引用原始标注证据、不可覆盖的最终人工判断。
4. **模型金标清单**：从仲裁金标中明确选择、结构可用且旅游标签为 `related/unrelated` 的唯一记录 ID 清单。

最重要的定义是：

> 原始标注不是金标；模型预测不是金标；重复候选不是金标。只有保存在 `text_post_adjudications`、引用人工证据的仲裁记录，才是本项目的文本清洗金标。

## 3. 研究边界：标什么，不标什么

### 3.1 本任务只标三条轴

每条帖子必须分别判断：

| 判断轴 | 标签 |
| --- | --- |
| 结构可用性 | `usable` / `invalid` / `uncertain` |
| 旅游相关性 | `related` / `unrelated` / `uncertain` |
| 商业属性 | `organic` / `promotion` / `uncertain` |

三条轴彼此独立。例如：

- 旅游广告可以是 `usable + related + promotion`；
- 青岛软件大会招商可以是 `usable + unrelated + promotion`；
- 普通游客攻略可以是 `usable + related + organic`；
- 登录墙通常是 `invalid + uncertain + uncertain`。

### 3.2 本任务明确不标

标注员不得判断或填写以下内容：

- 是否属于青岛：上游输入已经完成青岛范围定稿；发现明显范围异常时报告管理员，不创建城市标签。
- 目的地形象、情感、认知/情感/意动、游客动机等论文正式编码维度。
- 内容真假、攻略质量、审美价值、文笔、信息是否有帮助。
- 作者身份层级、影响力或是否“专业博主”。
- 图片是否需要清洗：本手册只处理文本；图片依赖导致文本无法判断时使用 `uncertain`。
- 是否删除帖子：标注只产生事实标签和金标，最终 `keep/review/exclude` 属于后续决策。

### 3.3 禁止的判断捷径

- 检索词命中不等于旅游相关。
- 出现“青岛”“栈桥”等词不等于旅游相关。
- 文本短、无标题、有水印、带广告或口语化不等于结构无效。
- `promotion` 不等于应排除。
- 模型分数、重复相似度或上一位标注员的结果不能替代人工判断。
- 不确定时不得为了“提高一致性”强行选择二分类标签。

## 4. 人员角色与职责分离

正式标注至少需要以下角色：

| 角色 | 职责 | 不得做的事 |
| --- | --- | --- |
| 项目管理员 | 冻结手册和候选构建、创建抽样、分配槽位、管理身份哈希、导入文件、生成报告 | 不得在导出后修改样本成员，不得覆盖原始标注 |
| 标注员 A | 完成 slot 1；独立判断三条轴并记录理由 | 不得查看 slot 2、模型分数和仲裁结果 |
| 标注员 B | 完成 slot 2；独立判断计划双标对象 | 不得查看 slot 1、模型分数和仲裁结果 |
| 仲裁员 C | 阅读同一对象的原始证据，处理分歧和 `uncertain`，形成最终金标 | 双标对象上不得与 A/B 为同一人，不得无证据改标签 |
| 数据管理员 | 保存受控 CSV、备份派生库、核验哈希和访问权限 | 不得把 UGC、作者身份、标注 CSV 或数据库提交 Git |

同一人可以在不同批次承担不同角色，但同一双标对象必须满足：slot 1、slot 2 和仲裁员是三名不同人员。系统以 64 位 SHA-256 哈希身份校验，不在派生库保存姓名。

### 4.1 身份哈希管理

身份哈希必须来自项目内部的随机假名令牌，不要直接对姓名、邮箱或工号做无盐哈希。数据管理员应在加密位置单独保存“人员—随机令牌—哈希”的映射，标注 CSV 只填写哈希。标注员、仲裁员和导入者可以各自拥有不同用途的令牌；人员退出项目后不修改历史哈希。

系统只接受 64 位十六进制 SHA-256，并在写入时统一为小写。管理员可在一次性临时派生库中用不含真实姓名的合成任务验证哈希格式，验证后销毁整个临时库；不要向正式派生库写入“测试后再删除”的记录，因为正式标注记录是追加式且不可删除。不得把随机令牌、映射表或生成命令的终端输出写入项目日志。

## 6. 标注对象长什么样

标注单位是一条帖子文本，对应唯一的 `source_post_id + source_version`。标准 CSV 会提供：

- `task_id`：当前槽位任务身份；不得修改。
- `sample_run_id`：抽样运行身份；不得修改。
- `source_post_id`、`source_version`：帖子版本身份；不得修改。
- `platform_key`：平台；只帮助理解结构差异，不改变标签标准。
- `assignment_slot`：1 或 2；不得修改。
- `normalized_model_text`：规范化后的标题和正文。
- 三条待填标签、理由代码、标注员哈希和时间。

### 6.1 规范化标记的含义

当前标准任务上下文包括平台、规范化标题和规范化正文，不包括模型分数、重复相似度、另一位标注员答案或最终决定。文本形态如下：

```text
[TITLE]
标题内容
[BODY]
正文内容
```

其中：

| 标记 | 含义 | 标注时怎样处理 |
| --- | --- | --- |
| `[TITLE]` / `[BODY]` | 标题和正文边界 | 不把标记本身当作内容 |
| `[URL]` | 原文包含链接 | 只知道存在链接，不推测目标网页内容 |
| `[MENTION]` | 原文包含 @用户 | 不推测被提及者身份 |
| `[TOPIC]…[/TOPIC]` | 原文话题标签 | 话题文字保留，可作为语义证据，但不能单独决定主旨 |
| `[EMOJI]` | 原文包含 emoji | 不猜测具体 emoji；结合其余文本判断 |

标题为空但正文有效是正常平台结构，例如：

```text
[TITLE]

[BODY]
栈桥夜景很好，晚上风大，建议带外套。
```

这条不因空标题而无效。

如果项目另行提供帖子图片或其他上下文，必须保证两位标注员看到完全相同、来源和版本均已冻结的材料，并且不暴露不必要的作者直接标识。当前标准 CSV 不包含图片；文本语义依赖图片时按本手册使用 `uncertain_image_dependent`。

## 7. 固定判定顺序

每条帖子必须按同一顺序判断：

1. **先判结构可用性**：是否存在可以阅读和归属到该帖子的文本证据？
2. **再判旅游相关性**：文本主旨是否属于旅行、游览或目的地体验？
3. **最后判商业属性**：文本是否具有明确推广、引流或交易意图？
4. 选择至少一个能够解释判断的 `reason_code`。
5. 做一次交叉检查：三条轴是否被错误捆绑，例如把广告自动判无关。

三条标签都必须填写。结构为 `invalid` 时，旅游和商业轴仍分别判断；如果由于空白、错误页或证据损坏而确实无法判断，则填写 `uncertain`，不是由程序自动联动。

## 8. 结构可用性标注

### 8.1 `usable`

满足以下条件时标为 `usable`：存在可读、可归属到当前帖子的文本语义，足以让人判断它在表达什么，即使之后旅游相关性仍可能为 `uncertain`。

常见情况：

- 标题为空但正文有效；
- 只有标题但标题表达了完整主题；
- 文本很短，但仍有可识别语义；
- 含广告、联系方式、价格、话题或链接；
- 语气口语化、错别字多或标点混乱；
- 内容与旅游无关；
- 主要信息不够充分，导致旅游轴为 `uncertain`。

### 8.2 `invalid`

`invalid` 只用于明确的结构失败：

- 标题和正文都为空或只剩空白；
- 全文是登录墙、权限提示、验证码或访问失败提示；
- 全文是删除、错误、加载失败或采集占位内容；
- 文本证据损坏，无法可靠读取；
- 无法确认文本属于什么内容对象或只是采集系统残片。

不要因为“不是旅游内容”而标 `invalid`。这应当是 `usable + unrelated`。

### 8.3 `uncertain`

结构轴的 `uncertain` 用于无法确定证据是否足以构成帖子内容，但又没有充分理由判定明确无效：

- 只剩 `[URL]`、`[MENTION]`、`[EMOJI]` 等无语义占位符；
- 内容状态不明，像占位符但也可能是作者原文；
- 文本极度残缺，无法确认是短内容还是采集损坏；
- 需要管理员核对源证据才能决定。

### 8.4 结构轴决策树

```text
标题和正文都没有可读内容？
├─ 是 → 明确为空/登录/错误/占位/损坏？
│       ├─ 是 → invalid
│       └─ 否 → uncertain
└─ 否 → 内容能被识别为一条帖子的文本表达？
        ├─ 是 → usable
        └─ 无法确认 → uncertain
```

## 9. 旅游相关性标注

旅游相关性判断的是**文本主旨**，不是某个词是否出现。

### 9.1 `related`

主旨涉及下列任一内容时通常为 `related`：

- 目的地或景点介绍、推荐、体验、评价；
- 行程、路线、攻略、游览顺序和停留时间；
- 面向出行的交通、住宿、餐饮、购物和费用信息；
- 游客体验、旅行见闻、打卡、度假和游记；
- 出发前决策、避坑、季节、天气、客流和预约提示；
- 目的地宣传、旅游产品、旅行社线路或酒店套餐；
- 能影响游客目的地认知和选择的城市传播内容。

一个实用检验是：

> 去掉具体地名后，文本是否仍主要在讲出行、游览、游客消费或目的地体验？如果是，通常标为 `related`。

### 9.2 `unrelated`

仅偶然出现地名、景点词或城市背景，而主旨属于其他领域时标为 `unrelated`：

- 人物籍贯、学校所在地、公司所在地；
- 体育赛事、会议、招聘或商业活动的举办地点，正文主旨不是旅行；
- 普通地方新闻、社会事件或政策通告，未面向游客和目的地体验；
- 商品名、品牌名、影视台词、歌曲、网络梗；
- 日常社交、个人情绪或本地生活记录，地点只作背景；
- 软件、工业、教育、医疗等专业内容，青岛只是发生地。

### 9.3 `uncertain`

以下情况使用 `uncertain`，并交给仲裁：

- 文本过短，只出现“青岛”“出发了”等，无法确认主旨；
- 关键语义完全依赖未提供的图片或视频；
- 同时存在旅游和非旅游主旨，无法确定哪一个占主导；
- 看起来像活动、餐饮或本地生活，但无法判断是否面向游客/旅行决策；
- 规范化后丢失了决定性上下文，不能可靠二分。

### 9.4 主旨判定的五步法

1. 用一句话概括文本“主要在说什么”。
2. 圈出旅游行为或目的地体验证据，而不是只圈地名。
3. 判断目标读者是否可能在进行出行、游览或目的地消费决策。
4. 去掉地名后重新阅读，检查旅游主旨是否仍成立。
5. 两种解释同样合理时选择 `uncertain`，记录具体不确定原因。

### 9.5 容易混淆的类型

| 内容类型 | 判断原则 |
| --- | --- |
| 本地餐厅探店 | 如果主旨是目的地餐饮体验、游客推荐或到访决策，标 `related`；纯日常聚餐且地点只作背景可标 `unrelated` |
| 演唱会/赛事 | 仅讨论比赛或明星通常 `unrelated`；同时提供跨城出行、住宿、游玩路线且旅行主旨明确时可标 `related` |
| 城市新闻 | 一般 `unrelated`；若直接影响游客游览、景区开放、交通和旅行决策，可标 `related` |
| 酒店/民宿广告 | 旅游轴通常 `related`，商业轴 `promotion` |
| 房产/招聘广告 | 通常 `unrelated + promotion`，即使出现青岛地名 |
| 城市宣传片文案 | 面向目的地认知与到访传播时 `related`，商业轴另判 |
| 交通信息 | 面向旅行到达、景点换乘或游客决策时 `related`；普通通勤事故新闻可能 `unrelated` |
| “如图”“看视频” | 文本本身不足以判断时旅游轴 `uncertain`，不得猜图 |

## 10. 商业属性标注

商业属性独立回答：文本是否包含明确的推广、引流、获客或交易目的。

### 10.1 `promotion`

存在下列明确证据之一时通常标为 `promotion`：

- 购买、预订、报名、咨询、私信、加联系方式等行动号召；
- 优惠、套餐、折扣、团购、限时价格或库存信息；
- 商家、机构或业务账号以获客为目的介绍产品/服务；
- 明示“广告”“推广”“合作”“赞助”“体验官”“探店合作”；
- 引导进入店铺、直播间、外部链接或其他账号完成交易；
- 招商、加盟、招聘中介、房产销售等非旅游商业推广。

### 10.2 `organic`

没有明确推广或交易意图，主要是个人表达、经验分享、客观信息或普通讨论时标为 `organic`。

以下内容本身不足以判推广：

- 提到品牌、酒店、餐厅或景区名称；
- 提到价格、门票或消费金额；
- 使用“推荐”“值得去”等普通经验表达；
- 带平台水印、话题标签或链接占位符；
- 内容写得像攻略或清单。

### 10.3 `uncertain`

商业意图证据不充分时标为 `uncertain`：

- 语气像推广，但没有行动号召或身份线索；
- 既像真实体验又像软广，无法判断；
- 链接目标、账号性质或合作披露在当前文本中不可见；
- 文本太短或结构无效，无法评估商业目的。

### 10.4 商业属性不改变清洗结论

`promotion` 只记录属性：

- `related + promotion` 可以保留为旅游目的地传播材料；
- `unrelated + promotion` 的排除依据是 `unrelated` 的人工确认，不是推广本身；
- 不允许用商业轴替代旅游轴。

## 11. 受控理由代码

当前导入器会把 `reason_codes` 规范化为 JSON，但 schema 尚未用枚举表限制每个值。因此正式标注必须使用下列受控代码；需要新增代码时先修订手册，不得自由造词。

### 11.1 结构理由

| reason_code | 含义 |
| --- | --- |
| `structure_valid_text` | 存在可读、可归属的文本语义 |
| `structure_no_title_valid_body` | 标题为空但正文有效 |
| `structure_empty` | 标题正文均无内容 |
| `structure_login_wall` | 登录、权限或验证码提示 |

## 16. 一致性检查

### 16.1 执行命令

```bash
.venv/bin/python scripts/annotation_adjudicate.py \
  --derived-db <DERIVED_DB> \
  --config configs/cleaning-v2.4.yaml \
  agreement \
  --sample-run-id <SAMPLE_RUN_ID>
```

### 16.2 怎样解释输出

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `incomplete` | 计划中的 slot 1/2 尚未全部完成 | 补齐缺失任务，不计算“通过” |
| `passed` | 三个轴均达到原始一致率和 κ 门槛 | 进入仲裁和金标冻结 |
| `supplement_created` | 至少一轴未达门槛，已冻结补充双标 | 导出补充 slot 1/2，完成后重算 |
| `supplement_exhausted` | 未达门槛，但抽样并集中已无未双标对象 | 暂停正式训练，负责人决定扩样或升级手册 |

三个轴分别计算：

- 结构可用性原始一致率与 κ；
- 旅游相关性原始一致率与 κ；
- 商业属性原始一致率与 κ。

每个轴都必须满足：原始一致率 ≥0.80 且 κ≥0.70。不要把三轴合成一个 κ，也不要只报告较好的轴。

## 17. 补充双标

分别导出：

```bash
.venv/bin/python scripts/annotation_export_tasks.py \
```

如果低一致性来自手册歧义，管理员应先收集分歧类型，正式发布修订版手册后创建新协议运行。不得一边标一边口头改变当前冻结手册。

## 18. 仲裁并形成金标

### 18.1 哪些对象需要仲裁

- 双标标签不一致的对象；
- 任一标注员选择 `uncertain` 的对象；
- 计划用于正式模型训练或正式比例报告、但目前只有原始单标的对象；
- 模型候选经过人工复核后需要形成最终相关性证据的对象。

为了保证所有正式结果都可追溯，建议正式抽样中的每条最终标签都形成一条仲裁记录：单标对象可由仲裁员确认原始记录；双标对象必须引用两条槽位证据。

### 18.2 仲裁员的工作方法

1. 先阅读当前手册，不看模型分数。
2. 阅读该对象的规范化文本和两条原始标签。
3. 分别处理结构、旅游和商业三条轴；某一轴一致不代表其他轴无需判断。
4. 对照理由代码，明确分歧来自主旨、结构还是商业意图。
5. 给出最终标签、理由和证据 ID；不要删除原始分歧。
6. 双标对象必须引用 slot 1/2 两条记录，仲裁员与两位标注员均不同。

仲裁不是强制二分。如果在完整现有证据下仍无法稳定判断，仲裁结果可以保留 `uncertain`；这是一条有效的完整金标，但不会进入 `related/unrelated` 二分类训练。

### 18.3 生成仲裁工作表

当前实现没有专门的 `export-adjudication` CLI。项目管理员需要用只读 SQLite 客户端从派生库导出两槽证据；该文件只交给仲裁员，不得回传给原标注员。推荐查询为：

```sql
SELECT
    a.annotation_id,
    a.sample_run_id,
    a.source_post_id,
    a.source_version,
    a.assignment_slot,
    a.annotator_hash,
    a.structure_label,
    a.tourism_label,
    a.commercial_label,
    a.reason_codes_json,
    a.guide_version,
    a.annotated_at_utc,
    r.normalized_model_text
FROM text_post_annotations AS a
JOIN text_sampling_runs AS s
  ON s.sample_run_id = a.sample_run_id
JOIN text_candidate_corpus_members AS c
  ON c.build_id = s.candidate_build_id
 AND c.source_post_id = a.source_post_id
 AND c.source_version = a.source_version
JOIN text_deterministic_results AS r
  ON r.task_id = c.task_id
WHERE a.sample_run_id = :sample_run_id
  AND a.guide_version = 'text-relevance-v1.0'
ORDER BY a.source_post_id, a.source_version, a.assignment_slot;
```

必须以只读方式打开派生库。导出后检查每个计划双标对象恰有 slot 1/2 两行；单标对象只有一行是正常的。仲裁工作表不得覆盖或改写查询得到的 `annotation_id`。

### 18.4 仲裁 CSV 必需字段

```text
sample_run_id,source_post_id,source_version,adjudicator_hash,
structure_label,tourism_label,commercial_label,reason_codes,
evidence_annotation_ids,decision_context,adjudicated_at_utc
```

`evidence_annotation_ids` 用 `|` 分隔。普通金标使用 `decision_context=gold`。模型复核使用 `decision_context=model_review`，并额外提供 `model_run_id`。

### 18.5 导入仲裁

```bash
.venv/bin/python scripts/annotation_import_annotations.py \
  --derived-db <DERIVED_DB> \
  --config configs/cleaning-v2.4.yaml \
  --input <SECURE_DIR>/post-adjudications.csv \
  --imported-by-hash <IMPORTER_64_HEX> \
  post-adjudications
```

导入成功后，每条 `text_post_adjudications.adjudication_id` 都是一个可引用的金标身份。金标仍保留 `uncertain`；“金标”表示人工程序已完成，不等于一定属于二分类。

## 19. 金标的三个层级

### 19.1 原始标注层

表：`text_post_annotations`

用途：保留每位标注员的独立判断，计算一致性，作为仲裁证据。不能直接当模型金标。

### 19.2 完整仲裁金标层

表：`text_post_adjudications`

用途：形成结构、旅游、商业三轴的最终人工判断。可以包含：

- `structure_label=invalid/uncertain`
- `tourism_label=uncertain`
- `commercial_label=uncertain`

这些都是合法金标，对质量报告和边界分析有价值。

### 19.3 模型可用二分类金标层

只有同时满足下列条件的仲裁记录才能进入旅游相关性模型：

- `decision_context='gold'`
- 手册版本为 `text-relevance-v1.0`
- `structure_label='usable'`
- `tourism_label` 是 `related` 或 `unrelated`
- 对应帖子版本存在于指定完整候选构建和泄漏构建；
- 每个 `source_post_id + source_version` 只选择一个 adjudication ID；
- ID 被显式写入本次 `GOLD_IDS.txt`，不使用“数据库最新标签”推断。

`commercial_label` 不参与该二分类训练；`promotion` 不改变 related/unrelated 标签。

## 20. 冻结模型金标清单

项目管理员从已审核的仲裁记录生成每行一个 ID 的文件：

```text
# text-relevance-v1.0 formal gold manifest
adjudication_id_001
adjudication_id_002
adjudication_id_003
```

可以先用以下只读查询生成“候选清单”，再由管理员逐条确认要纳入的唯一 adjudication ID。查询结果本身不能直接当正式清单，因为同一帖子可能存在多条历史仲裁：

```sql
SELECT
    adjudication_id,
    sample_run_id,
    source_post_id,
    source_version,
    structure_label,
    tourism_label,
    commercial_label,
    reason_codes_json,
    evidence_annotation_ids_json,
    guide_version,
    adjudicated_at_utc
FROM text_post_adjudications
WHERE decision_context = 'gold'
  AND guide_version = 'text-relevance-v1.0'
  AND structure_label = 'usable'
  AND tourism_label IN ('related', 'unrelated')
ORDER BY source_post_id, source_version, adjudicated_at_utc;
```

如果同一帖子版本有多条仲裁，负责人必须依据版本、证据链和更正记录显式选择一条；禁止使用 `MAX(time)`、“最后一行”或数据库隐式顺序自动选择。

冻结前必须检查：

- 没有空行以外的无效内容；注释只以 `#` 开头；
- ID 唯一；
- 每帖每版本唯一；
- 两类标签都存在；
- 所有记录结构为 `usable`；
- 所有记录来自正确手册版本；
- 没有 `uncertain`；
- 清单 SHA-256、生成时间、代码 Git SHA 和派生库备份 SHA-256 已记录；
- 定向样本与概率样本用途仍可追踪，未把定向样本用于总体比例估计。

清单不得提交 Git，因为它可间接关联正式 UGC。只在受控运行 manifest 中保存去标识化哈希和计数。

## 21. 近重复关系的人工金标

近重复关系与帖子旅游标签是两套独立任务。

### 21.1 导出候选对

```bash
.venv/bin/python scripts/annotation_export_tasks.py \
  --derived-db <DERIVED_DB> \
  export-duplicates \
  --candidate-build-id <CANDIDATE_BUILD_ID> \
  --output <SECURE_DIR>/duplicate-pairs.csv
```

原始复核标签为：

- `duplicate`：两条文本可视为相同内容、转载或仅有不影响主旨的微小变体；
- `not_duplicate`：只是同主题、同模板或共享词汇，内容并非同一；
- `uncertain`：当前证据不足。

候选相似度仅帮助排序，不能直接决定标签。原始 pair 复核导入 `duplicate-annotations`；第三人引用原始复核 ID 后导入 `duplicate-adjudications`。

### 21.2 与金标训练的关系

只有显式列出的、人工仲裁为 `duplicate` 的 relation 可与作者和精确重复一起构建泄漏 component。候选 pair、候选连通分量和人工确认 relation 不等于分析去重簇；它们不能传播旅游标签，也不能自动删除帖子。

## 22. 周期复核与金标更新

基线快照后每累计 2,000 个首次出现的 `source_post_id`，创建连续周期轮次：

```bash
.venv/bin/python scripts/annotation_export_tasks.py \
  --derived-db <DERIVED_DB> \
  --config configs/cleaning-v2.4.yaml \
  create-periodic \
  --candidate-build-id <NEW_CANDIDATE_BUILD_ID> \
  --baseline-sample-run-id <INITIAL_SAMPLE_RUN_ID> \
  --round-number <N>
```

每轮从 true-new 窗口与当前结构可用语料的交集中概率抽取最多 100 条。周期样本主要用于监测采集结构和模型表现是否漂移；其原始标注、仲裁和金标构建使用同一本手册。

出现以下情况时，即使未满 2,000 条也应由负责人评估是否创建新的协议/抽样运行，而不是私自扩展旧轮次：

- 新增平台或关键词；
- 抓取字段或文本结构改变；
- 标签手册升级；
- 模型在某平台的人工复核错误明显增加；
- 数据来源或范围声明发生变化。

## 23. 金标验收标准

一批金标只有全部满足以下条件才可交给模型：

### 23.1 样本和身份

- 抽样运行及相关周期/补充父对象为 `finalized`；
- 成员计数与 manifest 可重建；
- 每个帖子版本身份唯一；
- 手册、配置、候选构建和源快照身份明确。

### 23.2 盲标完整性

- 计划双标对象 slot 1/2 全部完成；
- 同一槽位没有重复记录；
- 两槽标注者不同；
- 标注员未接触模型分数或另一槽位结果。

### 23.3 一致性

- 结构、旅游、商业三个轴都报告原始一致率和 κ；
- 三个轴均达到原始一致率≥0.80、κ≥0.70；
- 未达标时已完成补充双标或明确停止原因；
- 不允许用部分完成的 pair 计算“通过”。

### 23.4 仲裁证据

- 每条正式金标都是仲裁记录；
- 双标金标引用两个不同槽位和不同标注者；
- 仲裁员身份符合独立要求；
- 理由代码来自当前手册；
- 原始标注和仲裁均未被覆盖。

### 23.5 模型清单

- 只含 `usable + related/unrelated`；
- 每帖每版本只有一个 adjudication ID；
- `related` 和 `unrelated` 两类都存在；
- 清单哈希、代码、配置和数据版本已记录；
- 测试集、验证集和训练集尚未由人工按期望结果手工挑选。

任一项失败时，状态应为“尚未准备好”，不能为了启动训练降低门槛。

## 24. 质量抽查与常见错误

### 24.1 管理员的日常抽查

建议每次导入前后检查：

- 非法枚举或空标签；
- 同一标注员同时占用两个槽位；
- 某位标注员异常集中使用一个标签；
- `invalid` 比例异常高，尤其是无标题平台；
- 所有广告被错误标成 `unrelated`；
- 只要出现青岛就判 `related`；
- `uncertain` 极少或极多；
- 理由代码与标签相矛盾；
- 时间、身份哈希或任务 ID 被改写。

抽查用于发现流程问题，不得在管理员本地直接修改标注文件“替标注员改答案”。修正必须形成新的追加记录或仲裁记录。

### 24.2 最常见的六个错误

1. 把“无标题”当作结构无效。
2. 把“青岛词命中”当作旅游相关。
3. 把“推广”当作不相关或应删除。
4. 在看不到图片时猜测图片内容。
5. 为提高一致性而回看另一位标注员答案。
6. 把原始多数意见当成金标，跳过证据化仲裁。

## 25. 伦理、隐私与数据管理

### 25.1 研究对象和标注员

UGC 作者不是本标注任务招募的参与者，但原始文本和作者标识仍可能涉及个人信息。标注员通常是项目研究成员；如果标注员同时作为研究参与者被分析其行为、耗时或认知，则需要另行制定参与者同意和伦理方案，不能沿用本手册默认设置。

### 25.2 最低保护要求

- 标注任务使用项目内部哈希身份，不在派生库保存姓名。
- 不向标注员提供不必要的作者直接标识、账号链接或访问令牌。
- CSV、派生 SQLite 和模型 artifact 保存在受控本地目录。
- 不使用公共网盘、聊天群文件长期保存或 Git 提交原始任务。
- 不把 UGC 上传到外部 LLM、云端分类 API 或未批准的标注服务。
- 明确访问人员、备份位置、保留期限和销毁方式。
- 发现敏感个人信息、违法风险或可能造成现实伤害的内容时，停止传播并报告项目负责人。

### 25.3 伦理状态

正式标注前，项目负责人应根据所在机构要求确认伦理审批、豁免或数据使用依据。本手册不能代替伦理委员会判断。未完成机构要求时，状态记为 `ETHICS_PENDING`，可以继续完善代码和文档，但不开始正式人工任务。

## 26. 标注员一页速查

每条帖子按以下问题回答：

1. **有可读、可归属的文本吗？**
   - 有：`usable`
   - 明确为空/登录/错误/占位/损坏：`invalid`
   - 无法确定：`uncertain`

2. **主旨是旅行、游览、游客消费或目的地体验吗？**
   - 是：`related`
   - 地名只是背景，主旨属于其他领域：`unrelated`
   - 太短、依赖图片或多主旨：`uncertain`

3. **有明确推广、引流或交易意图吗？**
   - 有：`promotion`
   - 没有：`organic`
   - 证据不足：`uncertain`

4. **最后复核**
   - 短文本不自动无效；
   - 广告不自动无关；
   - 地名不自动相关；
   - 不看模型和他人答案；
   - 不确定就写 `uncertain` 和原因。
